| DEC-048 | Script Intelligence (WF-01) can run against a screenplay_version in any status (`draft`, `in_review`, etc.), not only `approved_locked` | PRD §3's workflow-1 table lists `screenplay_versions (status approved_locked, is_production_canonical=true)` under "Storage", which could be read as a precondition, but TFD-SCR-004's actual requirement text only says AI "reads only from a specific `screenplay_version_id`" -- nothing about the version needing to be locked first. Requiring a lock first would block the realistic workflow of previewing/validating extraction on a draft import before deciding whether to lock it at all, and AT-SCR-004.1's own given/when/then ("WF-01 is started with screenplay_version_id=v2") names no status precondition either | Eng | Decided; revisit only if a future requirement explicitly restricts WF-01 to locked versions |
| DEC-049 | The screenplay-lock approval (`ApprovalRequestModel.scope="screenplay_lock"`) is decided through its own endpoint (`POST .../screenplay-versions/{id}/decide`), not routed through the generic `POST /approvals/{id}/decide` used by the 4 graph-review scopes | That endpoint's response (`ApprovalDecisionResponse`) reports `run_status`/`new_project_version`, concepts a screenplay lock doesn't have (locking a version doesn't itself bump `projects.current_version`, and "run status" means nothing for a non-workflow-run approval) -- forcing a shared shape would mean fabricating meaningless values. `apps/api/routers/approvals.py`'s existing scope-dispatch `else` branch (SEC-08: never silently route an unrecognised scope to a fallback) already 422s this scope correctly without any change; a comment there explains why, so a future reader doesn't mistake the omission for a bug | Eng | Decided; S-SCR-03's own screen is the decision surface, consistent with its screen spec |
| DEC-050 | A real bug found and fixed while testing TFD-SCR-002.2: the partial unique index guaranteeing "at most one canonical screenplay version per project/episode" silently did not enforce that for any non-episodic project | PostgreSQL's unique indexes default to `NULLS DISTINCT`: two rows that both have `episode_id = NULL` (every linear-structure project -- the common case) are *never* considered duplicates by a unique index, regardless of what else matches, because NULL is never equal to NULL. This would have let two revisions of the same non-episodic project both become canonical simultaneously, the exact thing AT-SCR-002.2 requires be impossible. Fixed with PG15+'s `NULLS NOT DISTINCT` clause (`postgresql_nulls_not_distinct=True`) on both affected indexes (`uq_screenplay_versions_one_canonical` and `_project_number`) -- verified directly against `pg_indexes` after the fix, and caught in the first place only because a genuinely concurrent (`threading.Thread`) test was written for the acceptance criterion rather than a sequential one | Eng | Decided; this PG15+ clause should be the default going forward for any future nullable-column unique index in this schema, not just this one |
| DEC-051 | A second real bug found at the same time: approving a revision could fail its own unique-index check against *itself*, with no concurrency involved at all | The fix superseded the old canonical and promoted the new one in a single `flush()`; SQLAlchemy's unit-of-work does not guarantee the UPDATE statement order matches attribute-assignment order, so if the "promote new version to canonical" statement happened to flush before the "supersede the old one" statement, both rows were briefly `is_production_canonical=true` in the same uncommitted transaction -- and Postgres checks a (non-deferrable; partial indexes can't back a `DEFERRABLE` constraint) unique index immediately per statement, not at commit. Fixed by splitting into two sequential flushes, superseding first. Also discovered that the straightforward way to test this acceptance criterion -- two `threading.Thread`-driven HTTP requests racing to approve, matching `test_version_concurrency.py`'s established pattern -- was itself flaky here, because (unlike that precedent, whose invariant is also enforced by an independent optimistic-concurrency check) nothing else makes the outcome deterministic when the two requests don't genuinely overlap inside the race window; replaced with a deterministic test that exercises the DB constraint directly | Eng | Decided; a future test of a similarly narrow DB-level race should default to exercising the constraint directly unless the surrounding business logic independently guarantees a deterministic loser (as DEC-050's sibling project-version race does) |
